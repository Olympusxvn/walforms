Subject: Mainnet Walrus HTTP publisher — 502 Bad Gateway on PUT /v1/blobs

Hello,

We operate WalForms (repository) — a Walrus-native form platform on Sui Mainnet. End users upload JSON definitions and submissions via the Walrus publisher HTTP API: PUT {publisher}/v1/blobs?epochs=5 with the raw body (file bytes).

Observed behavior

We consistently receive HTTP 502 Bad Gateway when calling community Mainnet publisher endpoints from browsers (fetch) and from Windows terminals (curl.exe, not PowerShell’s curl alias):

Endpoint Result
https://walrus-mainnet-publisher-1.staketab.org/v1/blobs?… 502 (short body: “error code: 502”)
https://publisher.walrus-mainnet.h2o-nodes.com/v1/blobs?… 502 (nginx HTML “502 Bad Gateway”)

For comparison, the same PUT pattern against a Testnet publisher (e.g. https://publisher.walrus-testnet.walrus.space/...) returns 200 and a valid blob ID, so our client request shape and network path appear sound.

Context from Walrus docs

  • Public aggregators and publishers — on Mainnet there are no public publishers without authentication, as they consume SUI and WAL.
  • System constraints — public infrastructure — public publishers have no formal availability guarantees.

Questions for operators

  1. Are these Mainnet HTTP publisher URLs expected to accept unauthenticated PUT uploads today, or must production use an authenticated publisher / CLI / self-hosted publisher only?
  2. Do the 502 responses indicate a known outage, misconfiguration, or upstream issue — and is there a status channel or ETA?
  3. Is there a canonical list of Mainnet publisher base URLs for app integrations? (operators.json documents aggregators extensively; publishers appear primarily under testnet.)

What would help

  • Confirmation of the supported integration path for Mainnet blob uploads for third-party apps (HTTP vs CLI vs authenticated publisher).
  • If 502 is unintended: tracking ID, timeline, or workaround until the service is healthy.

Thank you for your time.

Recommended handling (Đề xuất xử lý)

Practical mitigations for WalForms users, integrators, and demo recordings while Mainnet HTTP publishers are flaky or return sustained 502:

  1. In-app retries. WalForms uploadBlob retries each publisher on HTTP 502 / 503 / 504 with short backoff before trying the next configured base URL. This only helps transient gateway errors.
  2. Manual blob upload. If the builder shows the curl fallback, use curl.exe on Windows (never bare curl), then paste the returned blob ID into the UI.
  3. PowerShell without curl. Equivalent: Invoke-WebRequest -Method Put -Uri "https://<PUBLISHER>/v1/blobs?epochs=5" -InFile ".\form-definition.json"
  4. Production direction (per Walrus docs). For reliability on Mainnet: run your own publisher, use an authenticated publisher, or integrate the Walrus CLI with a funded wallet.
  5. Demos & judges. To prove the product surface when Mainnet HTTP is down, record against Testnet (e.g. Mysten testnet publisher). Testnet blob IDs are not interchangeable with Mainnet on-chain transactions — label footage clearly as testnet vs mainnet.
  6. Operator outreach. Send the issue summary above to the publisher hosts you rely on; reference this page URL for context.
